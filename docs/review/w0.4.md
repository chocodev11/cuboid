# W0.4 review (fail)

W0.4 fails on four blocking items. Most of the work is good. The key mapping follows arch 10.3 and fact F1: keypad digits, keypad operators and keypad Enter differ from the main block, modifiers have sides, the Super keys are the Windows keys, letters go by the logical key, and OS repeat is dropped. The window rules match ui 1.2, ui 1.3, app 1.2 and app 4.2 exactly (1000 x 700 at scale 1; 900 x 700 x S, so 1350 x 1050 at 1.5 and 1791 x 1393 at 1.99; the 0 and 30 000 position guards). Frame pacing is a pure function with tests. The composite test compares the whole frame byte for byte at scales 1 and 1.5 and again on a second frame, and it passed here on WARP ("Microsoft Basic Render Driver"). `cargo clippy -p cuboid-shell --all-targets -- -D warnings`, `cargo test -p cuboid-shell` (25 passed, none ignored; the crate has no oracle-gated tests), `cargo fmt -p cuboid-shell -- --check`, `cargo xtask ledger --wp w0.4` and `cargo xtask layering` are all green. The crate root forbids unsafe code, and the dependencies follow arch 3.3. The blocking items are these. A minimised window stops all application logic. The application cannot learn the window position it must save. Headless frames never give egui any key events. Lavapipe is not wired, and the GPU tests pass without running when no adapter exists.

## Blocking

1. `crates/cuboid-shell/src/event_loop.rs:206-215`: a minimised window stops calling `ShellApp::frame`, and the pending wake-up is cleared before the early return. `frame` is the application's only periodic call. Arch 14.6 puts job polling, flows, timers and commands there. So minimising freezes all application logic. app 1.1 says "The application keeps running when it loses focus (backups and uploads continue)", and app 12.1 runs the backup loop on a timer. Neither the ledger nor arch 17 records this deviation.
   - Scenario: the user edits a model and then minimises cuboid for an hour. The original writes a backup within `max(300, N * 60)` seconds. The port writes none until the window is restored. A finished background job or a pending upload step also waits for the restore.
   - Fix: when the client area is 0 x 0, still run `ShellApp::frame` (begin and end the egui pass, skip tessellation and painting). Pace it like an unfocused window, at most 10 Hz and only on a change or a due wake-up, and keep `self.wake`. Do not rely on `RedrawRequested` for these frames, because a minimised window may get no paint message. Drive them from `about_to_wait`. Add a pacing test and a ledger line for app 1.1.

2. `crates/cuboid-shell/src/contract.rs:73-107`, `crates/cuboid-shell/src/event_loop.rs:218` and `:301-352`: the application has no way to read the window position. `ShellEvent` has no move event, `FrameCx` has no window state, and the shell never calls `egui_winit::update_viewport_info`, so egui's `ViewportInfo::outer_rect` stays empty. app 4.2 and app 10.2 save `windowX`/`windowY` on quit and on Preferences OK. app 10.1 says "the window position is read into `windowX`/`windowY` just before each write". The shell restores a position (`ShellOptions::position`), but it never reports one, so the save half cannot be built outside this crate (arch 21.1 rule 1).
   - Scenario: the user moves the window to a second monitor and quits. The app has no position to write, so the next start opens at the default place, or at a stale stored position.
   - Fix: add `ShellEvent::Moved { x, y }` from `WindowEvent::Moved` with the raw outer position in physical pixels, in the same coordinates `ShellOptions::position` restores. Also report the position once after the window opens. Report it raw: a minimised Windows window sits at -32000, and the 30 000 guard already rejects that on restore. Optionally add the current position and the full-screen state to `FrameCx`. Add a ledger entry for app 4.2 (position save).

3. `crates/cuboid-shell/src/headless.rs:155-165`: `ScriptedInput::Key` reaches only `ShellApp::engine_key`. egui never gets an `Event::Key`, `raw.modifiers` is never set, and pointer buttons always carry `Modifiers::NONE` (line 162). In the window, egui-winit gives egui every key, the modifiers and the Copy, Cut and Paste events. Arch 14.5 builds the own text field on "egui's galley layout and input events". Arch 14.1 and arch 19.3 run UI snapshots and recorded input replays through `Headless` on "the same `ShellApp::frame` path". So headless and window frames differ for any keyboard input. The only way to fix that is to change this crate's public `ScriptedInput` handling.
   - Scenario: a replay renames an element. It types "abc", presses Backspace and then Shift-clicks to extend the selection. In the window the field shows "ab" with a selection. Headless shows "abc" without one, because Backspace and Shift never reached egui. The replay cannot match its recording.
   - Fix: in `feed`, keep the held modifier state from the engine keys (Shift, Control, Alt and Command, either side). Set `raw.modifiers` and use it on pointer and wheel events. For each key, push the `egui::Event::Key` that egui-winit would produce, including its folding of keypad keys (fact F1). Push `Copy`, `Cut` and `Paste` for Ctrl+C, X and V, as egui-winit does. Add a test that a scripted Backspace and a scripted Shift reach `ctx.input`.

4. `crates/cuboid-shell/src/headless.rs:56-67`, `:388-398` and `:410-412`, `parity/ledger/w0.4.toml:169-176`, `.github/workflows/ci.yml:35-37`: the acceptance criterion "headless frame capture on WARP and lavapipe" is only half done. CI installs no Mesa or lavapipe package on Linux. When `Headless::new` finds no adapter, both GPU tests print a notice and return, so they pass. nextest hides the stderr of passing tests, so the notice never shows. `software_first` also falls back to any hardware adapter, and the test does not check which adapter ran. Arch 17.4 M0-3 already notes that "a test that returns early counts as passed". The ledger entry is `tested` with no note that lavapipe is not wired.
   - Scenario: CI is green on ubuntu-latest, but no frame was rendered there. A future egui-wgpu change that breaks the composite on Vulkan or lavapipe goes unnoticed.
   - Fix: in the two headless tests, fail instead of returning when `CI` is set, and there assert `DeviceType::Cpu` and print the adapter name. Ask the integration role, which owns CI under arch 21.1 rule 2, to install `mesa-vulkan-drivers` on the Linux job. Until a CI run proves lavapipe, split the entry: WARP `tested`, lavapipe `implemented` with a note.

## Nonblocking

- `keys.rs:92-100` and `:204-211`: the physical fallback for letters also applies to keys that print punctuation on Latin layouts. On Dvorak, physical KeyZ prints ";" and still maps to Z, so Ctrl and the ";" key fires Undo, and the real "z" key does too. On AZERTY, the "," key (physical KeyM) maps to M, next to the real M key. Arch 10.3's intent ("Ctrl+Z works wherever Z is printed") suggests falling back only when the key prints a non-Latin letter, or nothing at all. This is within R9, but the ledger note only mentions the Cyrillic case.
- `keys.rs:152-168`: keypad keys map to Keypad* whatever the NumLock state, so with NumLock off, keypad 1 is still Keypad1 and keypad "." is KeypadPeriod rather than Delete. The original's behaviour is unknown. Record it as UNVERIFIED in the ledger.
- `event_loop.rs:261-281`: synthetic presses that winit sends when the window gains focus reach the app as ordinary key-downs. egui-winit drops them (winit issue 3543). A key still held when focus arrives can then fire its shortcut once. Consider a `synthetic` flag on `EngineKeyEvent`, so the dispatcher can update held state without firing chords.
- `headless.rs:72-101`: `Headless::new` does not check its input. A size of 0, a side above 8192 (the limit egui-wgpu requests) or a non-finite or non-positive scale makes wgpu panic or egui misbehave, where a `ShellError` would be better. `window.rs:162-166`: a NaN `ui_scale_override` survives `clamp` and becomes a NaN zoom. Filter it with `is_finite`.
- `headless.rs:116-120`: `Headless::frame` returns `Result<RgbaImage, ShellError>`, while arch 6 says `-> RgbaImage`. `FrameRequest::quit` (contract.rs:144) is also new. Both changes are sensible. Record them in arch 6 or 17.4.
- `headless.rs:178-184`: a scripted `ShellEvent::Resized` reaches the app, but the target and `screen_rect` keep their old size. Either resize the target or document that one `Headless` has a fixed size.
- `headless.rs:124-135`: the headless `RawInput` has no `max_texture_side`, so egui uses 2048. The window passes the painter's value (8192). Font atlas growth can then differ between headless and window frames. Pass `device.limits().max_texture_dimension_2d`.
- `pattern.rs:112-121`: `TestPattern::paint` does not snap its rectangle to physical pixels (arch 13.1 step 3). The tests only use aligned offsets. This is fine for a spike, but the doc comment should say so.
- `w0.4.toml:130-136`: the Left Alt bypass is "Not implemented", but the status is `unverified-spec`. Arch 14.1 and R10 ask for a best-effort detection plus the flag. Use `todo`, or implement the best effort.
- `event_loop.rs:127`: `focused` starts as `true`. A window that opens without focus is paced as focused until the first focus event. This is minor.
- `headless.rs:429-458`: the scripted-input test only checks what the app received. It does not check that egui got the pointer, wheel and text events, or that delivery happened before `frame`.
- Some implemented behaviour has no ledger entry: the non-sRGB surface check (arch 13.1 step 4, `event_loop.rs:181-186`), the disabled egui keyboard zoom (arch 14.1, `:166`) and keeping the physical size and S on a monitor change (ui 1.2, `:325-339`).
- `lib.rs:13`: `pub mod pattern` ships a spike helper in the library API. Keep it if W3.3 reuses it. Otherwise gate it behind a feature or move it to the example.

## Integration notes

- Integration role (CI): install lavapipe on the Linux job and run the GPU tests there. Consider `--success-output immediate` or `final` for GPU tests, so that adapter names and skip notices show up in the logs.
- W3.3 and W3.5 (renderer): the shell creates the one shared device with egui-wgpu's default descriptor. That means no optional features, `Limits::default()` with 8192 textures, and WebGL2 downlevel limits on GL. Tier A with instance-rate records (arch 13.5) needs `Features::INDIRECT_FIRST_INSTANCE` requested at device creation. `VERTEX_STORAGE` and `INDIRECT_EXECUTION` are downlevel flags and need no request. If W3.5 may pick instance-rate records, the shell needs a hook for optional features (in `ShellOptions` and `Headless::new`) before then.
- Arch 13.9: wgpu's default uncaptured-error handler panics. The renderer or the app should install `Device::on_uncaptured_error` and a device-lost callback through `FrameCx::gpu.device`. Nothing in the shell does this today.
- App wiring: F11 toggles full screen and also reaches the app, where menus 6.3 binds it to ElementsMaterial (ledger `app.4.4.shell-f11-conflict`). The app owner decides which wins. The app also never learns whether the window is full screen, but it needs that to store the windowed client size (app 1.1) instead of the monitor size. A minimised window reports `Resized { 0, 0 }`. The app must not store that size either.
- W1.9 (dispatcher): OS repeat is already filtered in the shell, as the W1.9 review expected. Synthetic focus presses do arrive as key-downs (see Nonblocking).
- W3.3 and W5 (view composite): register each view texture once, re-bind it on resize with `update_egui_texture_from_wgpu_texture`, and snap the view rectangles to physical pixels. The bit-exact result only holds for aligned rectangles. In the window, `pixels_per_point` is `scale_factor * (S / scale_factor)` in f32, which can differ from S in the last bit (1.50000006 at a scale factor of 1.25). That is harmless for nearest sampling, but no test covers the window path.
