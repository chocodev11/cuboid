# W1.4 review (fail)

W1.4 fails on one blocking item: the DDA reports hits on stored voxels when the active box is empty on one axis, which the setters of tools 2.4 allow. Everything else is in good shape. I checked all 24 vertices of the tools 7.6 table row by row against `CORNERS` and the typed `SPEC` table in the tests: positions, A, B and D all match. Face emission uses the right neighbour per direction (-Y j-1, +Y j+1, +Z k-1, -Z k+1, -X i-1, +X i+1) and fills the pools in `Dir::ALL` order. The 18 x 18 x 18 window reads all 26 neighbours, diagonals included, and applies the box rule to every cell, so culling, AO and the voxels themselves follow the coordinator's decision. AO codes (2 when A and B, else A + B + D) and factors 1.0, 0.9 and 0.8 are right. The record packing matches its documented bit positions. `expand_face` places the chunk at (16 i' c - 16, 16 j' c - 16, 16 - 16 k' c), adds the local vertex as the spec writes it, and multiplies all four colour channels by the factor. The DDA walks in index space with the same parameter as world space. It clips to the active box, treats a start inside a voxel as single-sided, pins the hit point to the face plane, returns the outward axis normal, and counts a hit at exactly `max_len`. Both twins are independent of the code under test: the literal mesher reads through `world.read` and the typed table, and the brute-force ray search tests every exposed front face. Only owned files changed (by modification time), the crate forbids unsafe code, and no indexing or unwrap reaches non-test code. Clippy with `-D warnings`, 83 tests (1 ignored), rustfmt, `cargo xtask ledger --wp W1.4` and `cargo xtask layering` all pass. The ignored timed test in release gave numbers close to the ledger: solid 23 ms and 3 ms, checkerboard 1684 ms and 308 ms, noise 1541 ms and 164 ms (one thread, then 16 threads).

## Blocking

1. `crates/cuboid-voxel/src/dda.rs:55` and `dda.rs:74-84` (ledger `parity/ledger/w1.4.toml:226`, `arch.13.7.dda-outside-box-and-grid`). When the active box is empty on an axis (`min == max`), a ray that crosses that plane gets `t_in == t_out` and passes the `t_in > t_out` test. The start cell is then clamped with `clamp(active.min, active.max - 1)`, which gives `min - 1` on that axis, a cell outside the box. `cell_at` ignores the box, so a stored voxel there counts as solid, and with `entry` set the function returns a hit. The mesher masks the same cell and draws nothing, so picking and picture disagree. The state is reachable. Tools 2.4 clamps `xmin` to `[-16, xmax]` and `xmax` to `[xmin, 32]`, so a handle drag can make them equal. A model box thinner than half a cell can also round to an empty index range (tools 7.2), and tools 7.2 keeps the stored voxels when the box shrinks.
   - Scenario: R = 16, a voxel at index (16, 16, 16), so x in [0, 1]. The user drags the x-max handle onto x-min at x = 1, so the active box on x is [17, 17). The viewport shows no voxels. A hover ray from (-3, 0.5, -0.5) along +X returns a hit with normal -X, point (0, 0.5, -0.5) and distance 4. The point is not even on the ray at that distance: the ray is at x = 1 when t = 4. Every ray that crosses the plane in front of a stored voxel does the same. The voxel pointer appears over an empty view, and the phantom hit can shadow an element behind it in the hover pick. The ledger says "Cells outside the active box are empty" and marks it tested. The proptest never draws an empty box (`lo` in 0..6, `hi` in 6..13).
   - Fix: return `None` at the top of `dda` when `active.min.cmpge(active.max).any()`. Add a unit test with an empty box on one axis and a stored voxel just below it, for an axis ray and an oblique ray. Let the proptest draw empty spans too, for example `hi` from `lo..13` per axis.

## Nonblocking

- `dda.rs:100-122`. With a zero direction and an infinite or NaN `max_len`, every `t_next` stays infinite, `t > t_out` is false, the step is 0, and the loop never ends. The doc requires a unit direction, but a hang is worse than a wrong answer. Return `None` when the smallest `t_next` is infinite, or when `d` is zero.
- `dda.rs:113`. `t_next[axis] += t_step[axis]` accumulates rounding over up to 762 steps per axis at R = 254. The drift is small (a few thousandths of a cell at most in practice), but it can move the hit point off the face a little and change the walk for rays very close to an edge. Computing `(boundary - q) / d` again for the stepped axis costs one division and removes the drift.
- `dda.rs:74-84`. A ray that starts exactly on the front face plane of a voxel (or on a box face, with the voxel just inside) is treated as starting inside it and misses that face, while the brute force would hit it at t = 0. Axis-parallel rays that lie exactly in a cell plane take the cell on the + side (`floor`). Orthographic views make on-plane rays more likely than the ledger's "never in practice". Pin both rules with a test and mention them in `arch.13.7.dda-grazing-rays`.
- `mesh.rs:585` test name and ledger `w1.4.toml:84` (`tools.7.6.quad-triangles`). "Counter-clockwise seen from outside" is wrong for the left-handed internal space (tools 1.2). The test checks the formula rule of tools 6.5, `(v1 - v0) x (v2 - v0)` along the outward normal, and that rule is right. In a left-handed frame those triangles look clockwise from outside. Use the tools 6.5 wording so W3.5 and W4.5 do not pick the wrong front face.
- `mesh.rs:104-112` and `mesh.rs:238-240`. The chunk fields have 6 bits (arch 13.5). Native 4.7 says readers must accept any R >= 1 within a memory limit. From R = 342 there are 65 or more chunks per axis, `cx << 12` runs into the `cy` bits, and faces are drawn in the wrong chunks without any message. Log an error and emit nothing when `chunks_per_axis() > 64`, or record the limit in the ledger so the loader caps R.
- `w1.4.toml:170` (`arch.13.5.mesher-is-a-pure-reader`). "Valid exactly while the world revision it started from is current" is not quite true: the output also depends on `world.ao`, a public field that does not draw a new `rev`. Mention it in the summary (see the AO note below).
- `w1.4.toml:93` (`tools.7.6.chunk-placement`). "The corner of a cell equals mapping::index_to_world" is tested only at c = 0.5, where both formulas are exact. At R = 24 the two operation orders can differ in the last bit. That is fine for P1; say "within rounding", or add an R = 24 case with the tolerance.
- `w1.4.toml:182` (`arch.18.chunk-meshing-throughput`). The arch 18 budget is for the S2 scene (R = 128, about 2 M faces, 8 threads), which is not measured. The noise case (24 M faces, 164 ms on 16 threads) suggests a wide margin, but the comparison with the solid world is loose. The criterion bench has no stored baseline yet (arch 18, W7.1).
- `mesh.rs:29`. Code 3 maps to 0.7. The spec defines only codes 0 to 2 and the mesher never emits 3, so this is harmless. The shader of W3.5 must use the same formula.

## Integration notes

- AO flag (W1.3 owner, needed by W1.5 or W1.6). Interop 16.1 says the option sets the world's AO flag "when the option changes". `ao` is a public field, and world.rs has no setter that marks every slot dirty and draws a new `rev`, because `dirty` is crate-private. If the port remeshes on an AO change, that setter must be added to `world.rs` before the model-property apply path is written. If the original only sets the flag and keeps the old meshes, record that as a quirk instead.
- Jobs (W3.5, W3.2). `mesh_chunk` takes the whole world. Share one `Arc` clone of the world per rebuild pass, not one per chunk; at R = 254 that is 110 592 slots. Do not drop results by the world `rev`: every write changes it, so during a long stroke every background job would be dropped and never land. Keep a per-slot generation that is bumped for each slot returned by `take_dirty`, and compare that.
- W3.5. Take the bit layout from `VoxelFace::new` and its accessors, the pool order from `Dir::ALL`, the vertex order and corner table from tools 7.6, the triangles `(q, q+1, q+2), (q, q+2, q+3)`, the factor `1 - 0.1 * code`, and alpha equal to the factor. Compare against `expand_face` for the goldens. `VoxelFace` has no `#[repr(transparent)]` and no `Pod` impl, so a zero-copy upload needs a change in `contract.rs` (W0.2) and an impl in this crate; copying the records also works.
- W4.5 (OBJ). A detailed-mode part is the chunk-local mesh plus the chunk position (interop 16.2, 16.3). `expand_face` returns `origin + local` in the same f32 order as `v + T`, which is right without smoothing. Smoothing averages chunk-local positions, and `expand_face` does not expose them. Byte parity with smoothing may need a chunk-local variant in `mesh.rs`. The original likely interleaves the faces of each voxel in one chunk mesh; the exporter can rebuild any voxel order from the local coordinates in the records (see `tools.7.6.face-order-in-pool`).
- W0.2 owner. The doc of `ExportVertex::color` in `contract.rs` still says "opaque"; tools 7.6 multiplies alpha too. The note of `arch.6.voxel-surface` in `w0.2.toml` ("Stub bodies ... log an error") is now stale for W1.4 as well.
- W3.2 and W2.x. `dda` needs a unit direction (hover length 1000). Normals are exact axis vectors, so the same-face gate of tools 12.2 can compare them with `==`. The hit point lies exactly on the face plane, so the inward and outward cells (`world_to_index_truncated` of `hit -/+ n * c / 2`) are robust.
