# Review: L6 R1, no console window, the terminal still works

Status: 2026-10-28. Reviewer: Opus. Scope: the uncommitted R1 of `docs/design/l6_release.md` section 2: the attribute in
`crates/cuboid-app/src/main.rs`, the new crate `crates/cuboid-term`, `snippets` in `crates/cuboid-mcp/src/connect.rs`,
`client_lines` in `crates/cuboid-app/src/mcp.rs` and its use in `library.rs`, the tests `guide.rs`, `views.rs`, the app
test of the view, `docs/mcp.md` 2 and 2.1, `docs/design/architecture.md`, `xtask/src/layering.rs`, `Cargo.lock`. Read
against the Rust 1.95.0 std source (`library/std/src/sys/stdio/windows.rs`, `io/stdio.rs`, `os/windows/process.rs`).
Run: `cargo clippy -p cuboid-term -p cuboid-mcp -p cuboid-app --all-targets -j 4 -- -D warnings` (clean),
`cargo test -p cuboid-term -p cuboid-mcp -j 4` (99 pass, 2 of them `twin.rs`; `twin.rs` 6 more times, all pass), the
app tests `the_view_carries_the_lines...`, `a_folder_that_cuboid_mcp_would_refuse...` and `mcp::tests` (4 pass),
`cargo fmt --check` of the three crates (clean), `cargo xtask layering` ("ok (28 crates checked)"). Probes in the
scratchpad, deleted after: a GUI-subsystem stand-in for `cuboid.exe` next to a copy of the debug twin; `rustc --test` of
a crate with `windows_subsystem`; the debug `cuboid.exe mcp --help` into closed pipes. Not run: release builds, the
GUI, the workspace tests, anything in a visible console.

Verdict: ready after one small major. The package does what section 2 asks: release builds are GUI programs, tests and
debug builds stay console programs, the twin forwards arguments, handles and full 32-bit exit codes, the check line
names `cuboid.com` only for a Windows release build while the three client lines keep `cuboid.exe`, nothing reads the
disk to decide it, and the guide and its pins follow. The implementer's claim about std holds for missing handles but
not for broken ones, and R1 makes broken handles a normal state: the twin dies on Ctrl+C or when its terminal closes
while the GUI child lives on with the inherited console handles. The logger's `eprint!` then panics, and the panic hook
logs through the same `eprint!`, which aborts the process (probed).

## Major

1. `crates/cuboid-app/src/logging.rs:178-180`, reached from the panic hook at `crates/cuboid-app/src/crash.rs:59`. The
   echo of every warning and error is `eprint!`, which panics on any write error that is not `ERROR_INVALID_HANDLE`
   (`io/stdio.rs:1165`, "failed printing to stderr"). Missing handles are fine: `get_handle` turns a NULL handle into
   `ERROR_INVALID_HANDLE` (`sys/stdio/windows.rs:72-73`), `is_ebadf` matches it (`:465`), and `handle_ebadf`
   (`io/stdio.rs:203`) makes the write a success and a read an end of input. A pipe whose reader closed (232, "The pipe
   is being closed") or a console that went away is not. The hook then calls `log::error!` (`crash.rs:59`), the second
   `eprint!` panics inside the hook, and std aborts. Probed with the debug binary, `mcp --help` with stdout and stderr
   both pipes whose readers were closed first: exit `0xC0000409` and a crash report "panic: failed printing to stderr:
   The pipe is being closed. (os error 232)" at `logging.rs:179`, from `mcp.rs:90`; with stderr open the same call
   exits 1 as the existing test expects. R1 widens it: `cuboid model.cubik` typed in a terminal runs the twin, and
   Ctrl+C or closing the terminal ends the twin only (the GUI child is attached to no console and gets no event), so
   the editor keeps running with handles of a console that may no longer exist, and its next warning can end it with
   unsaved work. The comment at `crash.rs:38` ("Best effort and panic free") is then not true. Fix: in `Logger::log`,
   `let _ = std::io::stderr().write_all(line.as_bytes());` in place of `eprint!("{line}")`, best effort like the file
   write at `:148` (`Write` is already imported). Test: a third case in
   `help_and_check_into_a_closed_pipe_exit_1_without_a_crash_report` (`crates/cuboid-app/tests/mcp_stdio.rs:450`) with
   `.stderr(writer2)` of a second pipe whose reader is dropped first: exit 1, no crash report. This is pre-existing code
   outside R1's file list, but it is the path the package was asked to clear, and the fix is one line.

## Minor

2. `docs/mcp.md:310`, the first row of 7 Troubleshooting: "Run the check of 2.1 ... `& "<program>" mcp --root "<folder>"
   --check`". The program of the line the user added is `cuboid.exe`, so the release build returns at once in
   PowerShell and prints nothing, which is what 2.1 now says it does. Fix: "`& "<folder of the program>\cuboid.com" mcp
   --root "<folder>" --check`, or the Try it line of the AI clients section", and one more row: "`--check` prints
   nothing and the prompt comes back at once | `cuboid.exe` is a window program | run `cuboid.com` beside it (2.1)".
   The guide test does not see table rows, so nothing pins this one.
3. `crates/cuboid-term/src/main.rs:13`. The twin starts whatever is named `cuboid{EXE_SUFFIX}` beside it, which is
   itself when it is installed under that name: as `cuboid` on Unix, where `EXE_SUFFIX` is empty, or as `cuboid.exe` on
   Windows by a slip in the copy steps of `docs/mcp.md:30-31`. Each copy then starts and waits on the next until the
   system runs out of processes. Fix, one guard before the `Command`:
   `if program == me { return Err(format!("{} would start itself", me.display())); }` (exit 2 with the usual line).
   No test: a regression would be the runaway itself.
4. For the coordinator's release probe (spec 4), not a code change yet. The GUI child writes to the console handles it
   inherits from the twin while it is attached to no console. If `GetConsoleMode` fails there, std writes the UTF-8
   bytes with `WriteFile` instead of `WriteConsoleW`, and the console decodes them with its code page; `--check` on a
   folder such as `D:\mô hình\đèn` would then print broken paths in the lines users copy. Probe `cuboid.com mcp --root
   "<non-ASCII folder>" --check` in both shells and `cuboid.com --version` after `chcp 437`. If the text is broken, the
   twin takes the child's stdout and stderr as pipes and copies them to its own handles (it is attached, so std writes
   UTF-16); that is safe only after fix 1, because a dead twin then closes the child's pipes.

## Nit

5. `crates/cuboid-term/tests/twin.rs:34-47`. Code 7 does not show that codes above 255 pass; Windows codes are 32 bits
   and `exit(i32)` keeps them (probed through PowerShell: 300 and `0xC0000005` came back exact). Use `exit 300` on
   Windows and keep 7 for `/bin/sh`. The stand-in is a console program, so the test cannot cover a GUI child; that is
   left to the probe, as the spec says. A renamed copy of `cmd.exe` run from a temporary folder matches the
   "renamed system binary" rule of some endpoint protection; if a managed machine blocks it, re-run the test binary
   itself as the stand-in (an environment variable selects a `main`-like branch). On Linux under `cargo test` (not
   nextest), copying an executable while the other test forks has a tiny `ETXTBSY` window; CI uses nextest.
6. `crates/cuboid-term/src/main.rs:19`. A child ended by a signal gives 1; shells give `128 + signal`
   (`std::os::unix::process::ExitStatusExt::signal`). The twin is a Windows tool, so this only matters if it ships on
   Unix; otherwise say in the comment that 1 is chosen.
7. `crates/cuboid-term/src/main.rs:27`. Exit 2 when `cuboid` cannot start is also `cuboid mcp`'s code for a refused
   folder or a failed check, so a script cannot tell them apart without stderr. 127, the shells' "not found", would
   be distinct; or keep 2 and name it in the guide.
8. `crates/cuboid-app/src/lifecycle.rs:65`, `:69` (`println!` for `--version` and `--help`), `:44`, `:91`, `:137` and
   `crates/cuboid-app/src/mcp.rs:79`, `:120` (`eprintln!`) panic on a closed pipe in the same way as finding 1, now
   that `cuboid.com --version` is a documented terminal use and a proof step (`cuboid --version | head -c0`). The W4
   review fixes noted the two `println!`. Fix: `write_stdout` for the two, `let _ = writeln!(io::stderr(), ...)` for
   the rest.
9. `docs/design/architecture.md:214-217`. The 3.3 graph lists every crate but the new one; add `term()` on the L6
   line, as the 3.1 tree already does.
10. `docs/mcp.md:137-139`. "copy or build the new `cuboid.exe` to the same path": add "and `cuboid.com`", since a new
    twin comes with each build until the installer of R3 does it.
11. Feedback cursor. Windows may show the app-starting cursor for about 2 s when a GUI program starts and shows no
    window, which is every `cuboid mcp` a client starts and every twin start of `--check`. std's switch for it
    (`CommandExt::startupinfo_force_feedback`) is unstable (issue 141010), and the clients start the server
    themselves, so there is no fix in safe stable code; note it in the probe.
12. A hand-typed `cuboid.com mcp --root X` (no `--check`) stopped with Ctrl+C leaves the child reading the console it
    inherited; std retries `ReadConsoleW` after `ERROR_OPERATION_ABORTED` (`sys/stdio/windows.rs:380-384`), so it may
    compete with the shell for input until the window closes. Not a documented use (the clients start the server);
    note it in the probe.

## The reported deviations

1. `not(any(debug_assertions, test))`: accepted. rustc applies `windows_subsystem` to the test harness too: `rustc
   --test` of a crate with the attribute gives PE subsystem 2 (probed). The spec itself says "tests stay console
   programs", so this implements its sentence. Under `cargo test --release` the integration test `mcp_stdio` then
   drives the real GUI binary through pipes, which is the handshake the spec's probe asks for.
2. `client_lines(root)` in `mcp.rs`, used by `check` and `clients_of`: accepted. One place for `current_exe`, its
   fallback and the console decision; `cuboid-mcp` stays free of what the app is built as and takes `Option<&Path>`.
   The twin's path is derived by name (`with_file_name`), with no disk read, so `clients_of` keeps "no disk is read
   here" (`library.rs:1409`) and the spec's "no file-system check on the UI thread". The predicate lacks the `test` of
   `main.rs`, so a `cargo test --release` unit binary, a console program, shows `cuboid.com`; harmless, since the lines
   describe the shipped program, and the app test mirrors the predicate, which pins it.
3. `cuboid-term` on layer 6: accepted. It depends on no workspace crate, so any layer passes; L6 beside the other tool
   binary `cuboid-cli` reads right; the lint requires an entry (`layering.rs`, "has no layer") and passes.
4. Not in `[workspace.dependencies]`: accepted. Every other crate has a line (rule 21.1.2 of W0.1, bin-only `cuboid-cli`
   and `cuboid-app` included), but a crate without a library target cannot be a dependency (cargo ignores such an
   entry with a warning), and the root manifest belongs to the integration role. Leaving it out is the honest state.

## Checked and sound

- Spec 2.1: the attribute and its comment; `#![forbid(unsafe_code)]` first in both binaries, and the workspace lint
  forbids it too. Spec 2.2: `cuboid-term` is safe std only, 30 lines with its doc, a console program in every profile;
  it finds `cuboid.exe` from `current_exe` (the real path even when started through PATH), passes `args_os` (no UTF-8
  panic in the twin), inherits the three handles and waits. Probed through the twin with a GUI stand-in: the arguments
  `a b`, `q"uote`, an empty one, `tr\ail\` and `ô` arrived intact, stdout, stderr and stdin went through pipes, and
  exit codes 300 and `0xC0000005` came back exact in PowerShell (Git Bash shows its own 8-bit view). `exit(i32)` in
  place of `ExitCode` is the right choice for 32-bit codes. Manifest style matches `cuboid-cli` (description, workspace
  fields, `[[bin]]`, `[lints]`, `tempfile` as a dev-dependency); the static CRT of `.cargo/config.toml` covers it.
- Spec 2.3: `snippets(exe, root, console)` builds the start command once (`command`), so the client lines are
  unchanged (`views.rs` proves only `check` differs by comparing the struct with `check` swapped back), and the check
  names the twin; every caller passes the new argument. `--check` prints only the four client lines, never the check
  line, so its output keeps `cuboid.exe`, as the stdio test expects. The guide's Try it line and `guide.rs` (with
  `TWIN`) agree; the rest of 2 and 2.1 matches the code; PATHEXT on this machine is `.COM;.EXE;...`.
- std without a console, as claimed: a GUI stand-in started through ShellExecute (no standard handles) ran `println!`,
  `eprintln!` and `read_to_string` on stdin and exited with its own code, 300, not 101. `INVALID_HANDLE_VALUE` as a
  standard handle maps to the last OS error, not to `ERROR_INVALID_HANDLE` (`sys/stdio/windows.rs:70-71`), and would
  still panic `print!`; no launch path of R1 passes it (Explorer gives none, the clients and the twin give pipes or
  duplicates of real handles).
- The protocol writer (`serve` returns the write error, exit 1), `write_stdout` for `mcp --help` and `--check` (exit 1,
  no panic), and the previous hook that the crash hook calls (std's default hook ignores write errors) are sound; the
  logger and the `println!`/`eprintln!` sites are findings 1 and 8.
- Ctrl+C: the twin is attached to the console and has no handler, so it ends at once with `0xC000013A`; the GUI child
  is attached to no console, gets no event and runs on. For `--check` and `--version` the output arrives after the
  prompt (cosmetic); for the editor it is better than before R1, when Ctrl+C or closing the terminal ended the editor
  itself, once finding 1 is fixed.
- `architecture.md` 3.1 row, `layering.rs` entry, `Cargo.lock` entry; files UTF-8 without BOM, LF.

## Fixes

Status: 2026-10-28. One line per finding, numbered as above.

1. Fixed. `Logger::log` echoes with `let _ = std::io::stderr().write_all(..)`, so neither the logger nor the panic hook
   that logs through it panics on a broken stderr. `help_and_check_into_a_closed_pipe_exit_1_without_a_crash_report`
   runs each case twice, with stderr open and with stderr a pipe whose reader is gone; before the fix the closed case
   of `mcp --help` exited `0xC0000409` (seen), after it every case exits 1 with no crash report.
2. Fixed. `docs/mcp.md` 7: the first row names `& "<folder of the program>\cuboid.com" mcp --root "<folder>" --check`,
   and a new row covers "`--check` prints nothing and the prompt comes back at once" (run `cuboid.com`, 2.1).
3. Fixed. `run()` of `cuboid-term` returns `<path> would start itself` (one line, exit 2) when the resolved program is
   `current_exe()`; the crate doc says so. No test, as the finding says. The comparison is exact, so a copy whose file
   name differs from `cuboid.exe` only in letter case on Windows would not be caught.
4. Not fixed, report only. The debug builds are console programs and no release build or visible console was allowed,
   so the case (a GUI child that holds the console handles of the twin) was not reproduced. What the tree shows: this
   machine has `OEMCP=437`, `ACP=1252`, en-US, so if `GetConsoleMode` fails in the child and the console decodes the
   `WriteFile` bytes with its output code page, `D:\mô hình\đèn` prints as CP437 mojibake unless the user ran `chcp
   65001`; nothing in the crates sets the console code page (`ansi_code_page` in `platform.rs` serves legacy files
   only), and `--check` writes plain UTF-8 through `write_stdout`. The release probe stays necessary; the pipes in the
   twin are the remedy if it shows broken text, and fixes 1 and 8 are what makes them safe.
   Update: the twin now relays pipes, so the probe no longer decides it. The child gets `Stdio::piped()` for stdin,
   stdout and stderr and three std threads copy them to the twin's own streams in 8 KiB chunks, flushed after each. The
   twin is attached to the console, so std writes the child's UTF-8 as UTF-16 and a non-ASCII path shows right in any
   console code page. Pinned by `the_input_of_the_twin_reaches_cuboid...` and
   `non_ascii_utf8_output_of_cuboid_arrives_byte_exact` in `crates/cuboid-term/tests/twin.rs`.
5. Fixed. The pass-through test of the twin exits with 300 on Windows and expects `Some(300)`; `/bin/sh` keeps 7. The
   notes on a renamed `cmd.exe` under endpoint protection and the `ETXTBSY` window on Linux are not fixed: no code
   change applies, both twin tests pass here.
6. Fixed. The comment at the exit code says that 1 is the code chosen when a signal ended the child.
7. Not fixed. 2 is the code the crate doc and `without_a_cuboid_next_to_it...` pin, and the line on stderr tells the
   cases apart; a change to 127 is the owner's call.
8. Fixed. `--version` and `--help` go through `mcp::write_stdout` (now `pub`; exit 1 on a closed pipe), and the
   `eprintln!` of `lifecycle.rs` (unknown option, file thread, window error) and `mcp.rs` (`refuse`, `serve_stdio`)
   are `let _ = writeln!(io::stderr(), ..)`. The closed-pipe test also runs `--version` and `--help`.
9. Fixed. `architecture.md` 3.3 lists `term()` on the L6 lines.
10. Fixed. `docs/mcp.md` 2.5 names `cuboid.exe` and `cuboid.com` for the update.
11. Not fixed. No safe stable code reaches `startupinfo_force_feedback` (issue 141010); left to the release probe.
12. Fixed by the same change as 4. The child no longer inherits the console: it reads a pipe, so a hand-typed
    `cuboid.com mcp --root X` stopped with Ctrl+C ends the twin, the pipe closes, the child reads the end of its input
    and stops, and it cannot compete with the shell for console input. The twin does not join its stdin relay (it may
    wait on a console read for ever); `exit` in `main` ends it.
