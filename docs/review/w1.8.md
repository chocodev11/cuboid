# W1.8 review (fail)

W1.8 delivers the registry (interop 4.1-4.4), the pipeline texts (interop 5.2, 5.4, 6.2-6.5), the BOM-aware
decoder, the permissive dialect `jsonlite` (native 9.4, interop 8.6), the tolerant `.mcpe` reader (interop
10.1), `NetJson`, `Lines`, minify, the naming helpers, the `.lnk` resolver with T-LNK-1, `write_atomic` and the
three fuzz targets. I checked every table row, label, message name, title, text and button against the spec
and found no wrong text. Lookup, dialog lists, loading box, status lines and writer-helper texts match. The
`.lnk` subset parser follows interop 28 step by step. The parsers bound recursion and allocation and cannot
panic on hostile input. `cargo clippy -p cuboid-io --all-targets -- -D warnings`, `cargo test -p cuboid-io`
(98 passed), `cargo fmt -p cuboid-io -- --check`, `cargo xtask ledger --wp W1.8` and `cargo xtask layering`
all pass. One blocking item remains. The `\uXXXX` tests of both readers lost their escapes, so they now
test plain characters. As a result the ledger claims key decoding and surrogate-pair decoding as tested, but
no test covers them. The code itself does both correctly. The fix is small.

## Blocking

1. `crates/cuboid-io/src/text/jsonlite/tests.rs:146-151` and `:176-180`, ledger
   `parity/ledger/w1.8.toml:335` (`native.9.4.unicode-escapes-only`).
   - What is wrong: the escapes were decoded before the file was written. The cases under the comment
     "\uXXXX, in both cases of hex digits" are now `""A""`, `""éé""` and `""xAyB""`. The case "A
     surrogate pair is one character" is a literal emoji. `keys_decode_unicode_escapes_too` parses
     `{"ab":1}`, which has no escape. So nothing tests that keys decode `\uXXXX`. Nothing tests
     lower-case hex digits or that two escapes form one character. Only `\\u0041` and the
     lone-surrogate cases still exercise decoding. The `tested` entry claims "also ... in keys". The
     `native.9.4.lone-surrogate` note claims the pair rule. Neither claim has a covering test.
   - Scenario: someone changes `Parser::object` to read keys without `unescape`, or changes `unescape` to
     turn each surrogate unit into U+FFFD on its own. Every jsonlite test still passes, and the ledger still
     says `tested`. A `.cub` or Minecraft JSON file with an escaped texture key such as `"\u0073ide"`,
     or with an escaped emoji in a name, would then import differently from the reference.
   - The same flattening affects `crates/cuboid-io/src/text/tolerant/tests.rs:69-70` (`""Aéé""` and a
     literal emoji). The tolerant reader's `\u` decoding is still covered for BMP characters by the
     serde_json differential test, but not for pairs.
   - Fix: restore the escapes in the raw literals. Examples: `r#""\u0041""#`,
     `r#""\u00e9\u00E9""#`, `r#""x\u0041y\u0042""#`,
     `r#""\uD83D\uDE00""#` (expected: one emoji), and `r#"{"a\u0062":1}"#` for the key test.
     Do the same in the tolerant test. Check the bytes with `grep -F '\u'` afterwards. The file-writing
     tool used by the agents decodes these sequences; it did the same to this review until it was fixed.

## Nonblocking

- `text/mod.rs:101-142` rejects `Infinity`, `-Infinity` and `NaN`. The documented .NET `Double.Parse` with
  the invariant culture accepts the culture's infinity and NaN symbols. A jsonlite number token can be
  `-Infinity`, because it starts with `-`. The choice is recorded under `native.9.4.separator-strictness`.
  But `interop.3.1.number-token-grammar` (`tested`) states "NaN, Infinity ... fail" as the invariant
  grammar, which overstates it. Either accept the symbols or move that clause to the unverified entry. In
  both cases, file a spec question. The same question should cover `1e999`: the port reads it as infinity,
  while older .NET parsers throw an overflow error, which would be a syntax error here.
- `text/value.rs:91-106`: `vec3` and `vec4` count items, not numbers, so `[1,"x",null]` gives `(1,0,0)`.
  Native 9.4 says "arrays of at least 3 ... numbers, otherwise the default is used". The item-count reading
  is plausible, but it is an interpretation. Record it as `unverified-spec` or follow the literal text. The
  saturation of out-of-range values in `as_i32` (`3e10` -> `i32::MAX`) is also a port choice. Today only the
  doc comment mentions it. The ledger should record it too.
- `text/tolerant.rs:125-127, 150-152`: the tolerant reader also stops at depth 128. The ledger records the
  limit only for jsonlite. Add it to the `interop.10.1.tolerance-subset` note.
- `text/mod.rs:66-86`: U+0085, U+2028 and U+2029 are written raw. This is recorded as unverified. If the
  original serializer is Json.NET, its default escaping writes these three as `\u0085`, `\u2028`
  and `\u2029`. Its hex digits are lower case, which supports the port's `\u001f`. Ask the spec
  team before the `.js`, `.jpm`, Zoxel and Stonehearth goldens freeze. If the answer is "escaped", only the
  serializer path changes. The hand-built writers' FIX-ALWAYS covers control characters only, so they stay
  raw.
- `text/tolerant.rs:34-45`: the reader ignores text after the root. `JsonConvert.DeserializeObject` turns on
  its additional-content check by default, so trailing text may fail in the reference. This is recorded as
  unverified. Add it to the same spec question.
- `lnk/tests.rs`: T-LNK-1 uses shortcut bytes that the test builds itself. Add one shell-created `.lnk` as an
  own fixture, with a real VolumeID and CommonPathSuffix. Then the subset parser is also checked against
  the layout Windows writes.
- `text/net_json/tests.rs:42-57` calls its document "the Stonehearth export (interop 27.1)" and writes
  `models` as a compact string array. Interop 11.1 states compact primitive arrays for the `.js` output only.
  Interop 27.1 refers back to the layout of 3.3. The API supports both layouts, so nothing here is wrong. The
  test is not a Stonehearth golden, and T-SH-1 has to settle that layout.
- `crates/cuboid-io/Cargo.toml` lists `glam`, `log` and `serde`, which the crate does not use.
- I did not build the fuzz targets (they need nightly). By reading, their calls match the crate API.

## Integration notes

- Pipeline texts live in `cuboid_io::pipeline` and `lnk::follow` (architecture 12.1). Architecture 14.7 wants
  every user-visible text in `cuboid-ui::strings`, checked against `parity/strings.toml`, which has no rows
  for them yet. The integration role should add the interop 5.2, 5.4, 6.2-6.5 and 28 texts, with `{App}`,
  or state that these functions are the catalogue for them.
- Architecture 12.5 names an `McJson` emitter in `cuboid-io::text`. The crate ships only
  `mc_json::minify` and `push_json_string`. The Minecraft JSON and resource-pack exporters must therefore
  own the tab, LF and trailing-space layout of interop 7 themselves. That works without changes here, but
  record it as a design note.
- The `.cub` importer (W1.7) and the `cubik29` Minecraft JSON importer share the dialect error and the model
  gate. That means `Invalid <KEY>` with "Invalid data found" (native 9.4, interop 8.1), `Invalid <KEY>
  Model`, `Generated Model` and `Inherited Model` (native 9.5 step 2, interop 8.2). `cuboid-fmt-cubik` and
  `cuboid-fmt-minecraft` sit on the same layer and cannot depend on each other, so `cuboid-io` is the only
  shared home. Decide before W1.7 starts. Either add these helpers here through the integration role, or
  accept two copies.
- For W1.7: `decode_bom` returns a `str`. The XOR of native 9.3 can run on `encode_utf16()`, and
  `String::from_utf16` turns the result back into a string without loss. The decoder maps lone surrogates to
  U+FFFD as the .NET reader does. XOR with the ASCII keys keeps high and low surrogates in their ranges.
  The result then goes to `jsonlite::parse`.
- `parse_double` (the invariant double grammar of interop 3.1) is private. The OBJ, QEF and schematic text
  readers need the same grammar. Making it public avoids copies with drifting rules.
- `FormatVisibility::default()` (a W0.2 contract type) sets `builtin_browser: false`. But the settings
  default `useNativeFileBrowser = false` means the built-in browser is on (interop 2.8). The app must build
  the value from settings, not from `Default`, or the `.lnk` entry disappears.
- The registry decides "has an importer" from capabilities, so `.lnk` passes validation without an
  `Importer` codec. The flow must therefore handle key `lnk` itself. It calls `lnk::target` and then
  `lnk::follow` off the UI thread, which reads the file system. It applies the result on the next frame,
  sets `Imported LNK: <path>` and `ep`, and never adds the path to recent files (interop 28, 5.2).
- Visibility is fixed when a `Registry` is built. If a Hide preference changes, the app must build a new
  registry and attach the codecs again.
