## W1.10 (fail)

W1.10 fails review on one blocking gap: the port's %author / %email values (app 10.2, menus 9.1) are never stored. The rest of the work is strong. The implementation is correct against app 10.1, 10.2 and 11, menus 9.1, 6.6 and 10.10, ui 2.2, 2.7 and 12.5, and arch 15. I checked all 53 key names, their write order and every first-run default against the app 10.2 table. Two values I verified independently: there are 37 boolean and integer keys and 14 nullable string keys, and the jiff timestamp in the test is right. Loading follows the spec. Missing keys take the menus 9.1 values (renderHiddenElements on, objCenterOnImport off, advAtlasSquare off, key strings null), as the W1.10 acceptance asks, and the conflict with app 10.2 and review claim 13 is recorded as unverified-spec. D10 is applied per key: an unusable boolean or integer, a null signature template or a null or unknown theme takes that key's first-run value, and nullable strings keep null. An empty file, a null file or a missing file is a fresh start, and a non-JSON or non-object file is moved to .bad. Saving writes pretty JSON with the version first and unknown keys kept in order, through a temporary file and a rename (D8). Recent files are identified by full path, stored oldest first and shown newest first, honour a stored max and never list .lnk files. The legacy import uses the values the app passes in and calls no OS APIs. Clippy, tests, fmt, ledger and layering are all green; the crate forbids unsafe code and touched nothing outside its paths except its own ledger file and Cargo.lock. The fix: the Cuboid section needs typed author/email fields (empty by default) with a round-trip test and a ledger entry; ideally the D2 and D5 opt-ins are added in the same change so later network work needs no API change to this crate. The non-blocking items are a Debug derive that prints the Sketchfab token, two log lines the specs quote that differ in text, small ledger wording and coverage slips, all-or-nothing reading of saved locations, and missing durability and case-folding details.

### Blocking

1. `D:/evkey/cuboid/crates/cuboid-settings/src/cuboid.rs`: The port's %author / %email values are never stored, and the ledger does not mention the gap. The signatureTemplate row of app 10.2 says: "Port: `%author`/`%email` from an optional user profile setting (empty by default)". menus 9.1 (General / Signature) says "`%author` / `%email` take values cuboid stores (empty when unknown)". This crate owns the data and persistence of app 10 (arch 3.2), yet neither Settings nor the Cuboid section has a field for them. The unknown-key map `extra` is pub(crate), so no other crate can reach such a value either. Under 21.1 rule 1, later packages (W6.2 Preferences, the signature expansion behind the native save description of native 4.x `d`) cannot add the field without changing this crate's API.
   - Fix: Add `author: String` and `email: String` to `Cuboid` (camelCase keys `author`/`email`, default empty), read them with `take` in `Cuboid::from_map`, and extend `cuboid::tests::every_key_round_trips` to cover them. Add a ledger entry (spec "app 10.2"). Mark it unverified-spec if you pick the key names yourself, since the spec names none. In the same change you may add the persisted opt-ins of D2 (skin lookup, app 9.7) and D5 (update check, app 18.2), both default false, so that W8.5 does not need a later API change to this crate.

### Nonblocking

- Settings, Loaded and Legacy derive Debug. That prints the Sketchfab token, and for Legacy the raw cubikdata.json bytes. Arch 16 and D3 say tokens are never logged. A hand-written Debug that redacts `sketchfab_token` (and `data` in Legacy), or a small secret newtype, would remove this risk instead of relying on the caller note.
- Two log lines the specs quote are not emitted with their exact text, which arch 16 requires. The crate never logs "CubikData: Fresh data created" (app 1.2 step 5), so either the app must log it on Origin::Fresh or `load` should. menus 10.10's "Not enough arguments" is logged as "settings: saved location skipped: not enough arguments", and the same message is also used for an unknown list name, flag, type or date, where it is wrong.
- Ledger accuracy. `app.0.2.settings-d8-atomic-write` lists `store::tests::an_unreadable_path_is_an_error`, which is a load test and covers nothing about atomic writes. The summary of `menus.9.1.settings-missing-key-defaults` says the key strings are "(empty)", but the code stores None, written as null. That matches review claim 13 and behaves the same, but the entry should say null and name the choice.
- A missing key takes None for the five key strings, and that is written back as `null`. menus 9.1 says "(empty)". The behaviour is the same (built-in bindings), but the bytes written differ from "". Keep the choice and state it in the ledger note.
- In the cuboid section, `locations` is read with a strict serde Deserialize. One malformed Location (for example an unknown `kind`) therefore drops the whole value, all favourites included. Reading the entries one by one and skipping bad ones, as `recentFiles` already does, would match the spirit of D10 better.
- Cuboid::from_map repeats `take(&mut map, "key", &mut cuboid.f, &first.f)` ten times (about 50 lines after rustfmt). A small local macro or the table approach of schema.rs would be shorter and could not drift. This is style only.
- `schema::tests::there_are_37_flag_and_integer_keys` only counts entries of the test's own FRESH fixture, so it adds little. The count is already implied by the null and round-trip tests.
- Locations::from_legacy removes CR as well as LF. menus 10.10 removes only LF. This is harmless, since the original writes LF, but it is an unrecorded leniency.
- write_atomic does not fsync the parent directory after the rename. On Linux and macOS the rename may not survive a power loss, although the old or new content still remains. This is a durability nit, not a parity issue.
- Recent-file paths are compared case-sensitively on every OS. On Windows, the same file opened through differently cased paths (for example drag and drop versus a typed path) gives two entries. Either the app canonicalizes paths before calling add/remove, or the crate compares case-insensitively under cfg(windows).

## W1.3 (fail)

W1.3 is close to done: build, clippy -D warnings, 46 tests, rustfmt, rustdoc and the ledger check all pass, and only owned files changed. I checked against the spec text the tools 7.2 mapping formulas and test vectors, the slot order (cx*n+cy)*n+cz, the x-y-z scan order, the persistence flags (EmptyWritten after erasing one by one, dropped on restore), copy-on-write, and the lint and unsafe rules; all of them are correct. The writer matrix with the port's dirtying, the model-based writer proptest, and the restore twin against the full-writer replay are meaningful tests. The verdict is still fail, for three blocking issues. (1) from_snapshot dirties only the chunks that have cells, so chunks emptied by an undo or load keep their old meshes, and restoring an empty snapshot gives a world with no dirty bit (one of the tests asserts this). (2) The tools 7.2 rule that a model box change dirties the affected chunks has no API: active_box is a public field with no setter and the dirty set is private to the crate, and the ledger does not record the requirement. (3) The ledger marks native 6.3 load behaviour as tested and calls from_snapshot the load path, but no loader exists in W1.3, and from_snapshot cannot reproduce the file-order palette for files that are not in canonical order. All three fixes are small.

### Blocking

1. `D:/evkey/cuboid/crates/cuboid-voxel/src/world.rs`: from_snapshot (lines 140-176) marks only the restored chunks that hold cells as dirty. A chunk that had a mesh in the live world but is empty after the restore is never re-meshed. The scene meshes only what take_dirty returns (arch 13.5 Jobs; journal VOXEL_CHUNKS is defined as take_dirty), so the old geometry stays on screen. Worst case: restoring an empty snapshot gives a world that is not dirty at all, and the test restoring_a_world_with_no_cells_gives_an_empty_world asserts exactly that (!is_dirty()). Scenario: set up voxels, paint one voxel, undo. The world comes back empty with no dirty bit, tools 7.6 schedules no rebuild, and the undone voxel is still drawn. The original clears the world in place before rewriting (tools 7.10), so every chunk it had allocated is rebuilt. The doc claim 'so the whole world is meshed again' does not hold.
   - Fix: In from_snapshot, mark every slot dirty (world.dirty.insert_range(..)); meshing an Unallocated slot costs nothing and just drops its range. Alternatively, restore into the live world and mark the union of the old and new allocated slots. Then: update the doc comment; change a_restore_marks_every_chunk_with_cells_dirty and restoring_a_world_with_no_cells_gives_an_empty_world to expect a fully dirty world; reword ledger entry arch.9.1.restore-fast-path.
2. `D:/evkey/cuboid/crates/cuboid-voxel/src/world.rs`: Tools 7.2, last bullet, is missing: when the model box changes, the affected chunks must be marked dirty and the world flagged dirty (port: remesh every affected chunk, always on, arch 17.2). active_box is a pub field with no setter, and dirty and mark_dirty are pub(crate). So the owner of the model box setter (tools 2.4 'notifies the voxel world', W1.5/core) cannot dirty anything, and only world.rs can provide the API. The ledger does not mention the requirement at all: it is neither tested nor unverified-spec. Scenario: shrink the model box with a handle drag and set world.active_box = mapping::active_box(new_box, res). Reads outside the new box now return 0, but no chunk is dirty. The meshes along the changed sides keep showing voxels that are now outside the box, and the faces newly exposed at the boundary stay missing until some unrelated write.
   - Fix: Add a public setter, for example VoxelWorld::set_active_box(&mut self, active: IBox3). It stores the box, marks dirty every chunk that overlaps the cells whose readability changed (the slabs between the old and new box faces, grown by one voxel because the mesher's neighbour reads and AO cross the boundary), and draws a new rev so stale mesh jobs are dropped. Add a test (a box shrink and a box grow dirty exactly the touched chunks and nothing else). Add a ledger entry, for example tools.7.2.model-box-change-dirties, P4, noting the port deviation from the original's 'first changed side only' quirk (arch 17.2).
3. `D:/evkey/cuboid/parity/ledger/w1.3.toml`: Entry native.6.3.vx-load-writes-through-the-full-writer is marked 'tested' with the note 'VoxelWorld::from_snapshot is the load path'. The VoxelSnap doc in world.rs says the same. W1.3 implements no loader, and the listed tests only compare from_snapshot with a replay in slot order. from_snapshot cannot reproduce native 4.7/6.3 for files that are not in canonical order. Cubik writes the listed records in file order through the full writer, so the palette follows file order, and duplicate chunk records add every colour they carry. A VoxelSnap loses record order and duplicates, so a file with chunks or voxels out of cx,cy,cz / x,y,z order, or with repeated records, gets a different palette. That changes palette and VOX export indices. The 'tested' status overclaims another package's requirement, and the note points loaders at a path that is wrong for such files.
   - Fix: Re-scope the entry to what W1.3 proves: from_snapshot equals a full-writer replay in slot and scan order, which is the undo-restore and canonical-file case. Either drop the native 6.3 entry or mark it unverified-spec/implemented, with a note that a loader of non-canonical files must replay records in file order through write_many(.., WriteKind::Full), or check the order first, and that the native 6.3 entry belongs to W1.6/W1.7. Correct the VoxelSnap and from_snapshot docs the same way.

## W1.9 (fail)

W1.9 is mostly solid. Clippy with -D warnings, the 42 tests, fmt and the ledger check all pass, and cuboid-shell and cuboid-core still compile against the new API. I checked the data against the spec myself: all 41 menu tables match menus 2.1-2.8, 3.1-3.8 and the menus 6.3 binding table. The 58 + 3 = 61 bindings match exactly (count, chords, menus, A/U flags, no duplicate chords). Engine key names, binding strings with the leading-comma quirk and the held-map defaults match menus 6.4/6.6. The dispatcher's press-order, modifier, keypad, mouse-button and enable gates are right, and strict mode follows the original frame algorithm. The tests read the spec text directly and are meaningful. There are two blocking spec deviations, both small to fix. (1) `HeldMap::set_custom` turns an all-`None` binding back into the built-in keys, so a string of only unknown names, which per menus 6.6 gives no key, cannot be expressed; only the empty string should mean built-in. (2) `Dispatcher::key_down` records keys while the modal flag is set, but menus 6.2 step 1 stops before the held list is updated. As a result, Ctrl pressed under a dialog followed by Z after it closes fires Undo in port mode. That deviation is not in the ledger and not covered by the event-ordered switch. Integration items: parity/strings.toml still has no menu rows (arch acceptance mentions them), the W0.2 ledger entries are stale, it is open whether ActionId covers the ui 6-8 panel buttons, and the menus 1.7 enable model sits in core/ui instead of MENUS.

### Blocking

1. `crates/cuboid-actions/src/held.rs`: `HeldMap::set_custom` treats an all-`None` key array as "restore the built-in keys". Menus 6.6 separates two cases: an empty string means the built-in default, and an unknown name gives "no key". So a non-empty string made only of unknown names ("Nope") has to leave the binding with no keys for the session; the canonical text "" is stored and Preferences shows "". Because `parse_binding("Nope")` and `parse_binding("")` both return `[None; 4]`, the API cannot express the spec's behaviour. With this API every caller would put the built-in keys back. The ledger entry `menus.6.6.custom-held-keys` ("an empty binding restores the built-in keys") is marked tested against a misreading of the spec.
   - Fix: Make `set_custom` store the keys exactly as given, so all-`None` means a binding with no key. Apply the empty-string rule at the string level, e.g. `HeldMap::apply_custom(b, text: &str)`: a trimmed empty text gives `builtin(b)`, any other text gives `parse_binding(text)`. The alternative is to expose the built-in keys so the settings caller can do this itself. Update the test: an unknown-only string gives no keys and the empty string gives the built-in keys. Fix the ledger summary to match.
2. `crates/cuboid-actions/src/dispatch.rs`: `Dispatcher::key_down` records the key in the held list before it checks `gate.modal`. Menus 6.2 step 1 stops all processing while the global modal flag is set, so a key pressed under a modal window never enters the held list. `frame_strict` does this correctly. The difference is visible in port mode. Press Ctrl while a message box or dialog is open, close it, then press Z: the port fires Undo, the original fires nothing. The event-ordered switch (arch 10.3, 17.2 `event_ordered_shortcuts`) only sanctions dropping the frame quirks (one key per frame, a mouse press cancels the frame), not the modal stop. The choice appears only in a doc comment. No ledger entry or deviation records it (`menus.6.2.gates` is plain `tested`), which breaks the 'never guess silently' rule and the parity-first principle (arch 2.1, 17).
   - Fix: In `key_down`, return early on `gate.modal` before `self.press(k)`, as `frame_strict` does. Update the doc comment. Add a test where Ctrl goes down under a modal gate and then Z under an open gate, and nothing fires. If the owner prefers to keep recording, it has to go in as an arch 17.3 deviation with a ledger note or an `unverified-spec` entry instead.
