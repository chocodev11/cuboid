# W1.2 review (fail)

W1.2 fails on two blocking items. The general file decoder does not enforce the area limit that the ledger claims for every decoder. And `Image` has no image name (`tx.n`), which W1.5 and W1.7 need. Everything else is strong. All ten format codes of native 4.5.1 decode with the right byte order and re-encode to `level_len` bytes. Re-encoding the decoded result gives the same bytes, and the 16-bit and 32-bit formats are lossless. DXT blocks follow the bottom-up rule: block row 0 is the bottom of the image, and texel row 0 of a block is its lowest row. BC1 three-colour mode, BC3 four-colour mode and both BC3 alpha modes are correct. I checked the DDS and TGA loaders byte by byte against tools 5.10, quirks included. I recomputed the signature vectors for 1252 and 1258 from the code page tables, and they are right. Every raster footprint of tools 13.2 matches its formula: the diameter-7 disc, the loop bounds of small brushes, the half-to-even square, the `err = dx + dy` Bresenham line, fill with T and T/2 similarity, noise and magic. The gutter fill matches tools 5.4 and interop 16.7.7, including the wrap across row ends and the rule that texel 0 is never a source. AlphaStats agrees with brute-force counting on every crop. Nothing contradicts native 4.5.3. ARGB32 is A, R, G, B. Rows are never flipped, so the recut `particle` hash survives. The strict recut can be built from `format::encode(ARGB32, ..)` and `Image::from_stored`. Clippy (`-D warnings`), 87 tests, fmt, `cargo xtask ledger --wp W1.2` and `cargo xtask layering` all pass. The crate forbids unsafe code, its dependencies match arch 4.1, and both fuzz targets type-check.

## Blocking

1. `crates/cuboid-image/src/file.rs:151-157` (ledger `parity/ledger/w1.2.toml:429`). `decode_other` limits only the width and the height (16384 each). It never checks `MAX_TEXELS` (2^26). The ledger says that sizes from files are limited to 2^26 texels before anything is allocated, and that "the decoders refuse larger headers". That is not true for PNG and JPEG. The doc of `MAX_TEXELS` (`contract.rs:21-23`) also says a huge header cannot make a decoder allocate more. But `into_rgba8` allocates `w * h * 4` beyond the `image` crate's 512 MiB `max_alloc`.
   - Scenario: a PNG of a few kilobytes, 16384 x 16384, 8-bit grey. The `image` crate allocates 256 MiB to decode it, then `into_rgba8` allocates 1 GiB. The result is an `Image` that `check_size` refuses. The `.cubik` reader is told to call `check_size` first (`contract.rs:26-27`), so it would refuse the port's own saved texture when the file is reopened. A legitimate 8192 x 16384 PNG does the same thing: the width-only slot downscale of tools 5.10 (slot 8192, D-P7) does not shrink it.
   - Fix: in `decode_other`, call `ImageReader::into_decoder()`, read `ImageDecoder::dimensions()`, run `check_size`, and only then call `DynamicImage::from_decoder`. Add a test with a small 16384 x 4097 grey PNG that must give `TooLarge`. Correct the `MAX_TEXELS` doc. If you want to keep the current behaviour instead, narrow the ledger summary to DDS, TGA and records. The decoder must still not produce images that `check_size` refuses.

2. `crates/cuboid-image/src/contract.rs:193-205`. `Image` has no image name. Tools 5.14 says "Every entry's image carries an internal name, persisted with the image (`tx.n`)". Tools 5.1, 10.14 (paste keeps the "image name") and native 4.5.2 (the copy keeps the source's image name) say the same. Native 4.5.3 says the recut sets `n` = "". Arch 3.2 makes this crate the owner of `Image`. Neither `TextureEntry`/`TextureSource` nor `Mesh`/`Submesh` in `cuboid-model` has a place for the name.
   - Scenario: W1.7 reads a texture record with `tx.n` = "e_particle", and the user paints on it. The edited record has to be re-encoded, and nothing holds "e_particle" any more. The same happens to mesh textures (`me[].tx`, `me[].sm[].tx`), which are bare `Option<Arc<Image>>`. A shortcut that shares the target's `Arc<Image>` has to show the target's name. The Minecraft export name (tools 5.14) is built from the image name. The strict recut (`atlas_recut_argb32`) must set the name to "".
   - Fix: add a name field to `Image`, for example `pub name: Arc<str>`, empty by default. `Clone` and `edit()` keep it, and `decode_file` leaves it empty: the loader sets the file stem (tools 5.10 step 6). Add it to the arch 6 sketch. If the owner prefers the model to hold the name, record that in arch 6 and in the W1.5 contract before W1.5 starts. Then this crate needs no change.

## Nonblocking

- `contract.rs:167-168`. The placeholder clamps each side to `MAX_SIDE`. For a record with a side above 16384, `rgba()` is shorter than `w * h * 4`. `encode_png` then hits the buffer-length `assert_eq!` in `image` 0.25.10 (`src/codecs/png.rs:741`) and panics. Readers are told to call `check_size` first, so this needs a contract violation. Still, the ledger (`w1.2.toml:441`) says "any record". Make `encode_png` compare `img.rgba().len()` with `w * h * 4` and return `ImageError::Encode`, or narrow the ledger to records within `check_size`.
- `format.rs:50-55, 125-128`. The 5-bit and 6-bit channels of RGB565 widen by bit replication. The spec does not give this rule. An engine that goes through float colour (`v / 31`, then rounded to a byte) gives a different value: 5-bit 3 becomes 25, not 24. The ledger records the Alpha8 colour and the 4444 layouts as `unverified-spec`, but not this. Add an `unverified-spec` entry. The 565 endpoints of the DXT blocks use the same expansion, and the existing rounding entry covers only the interpolation.
- `w1.2.toml:224`. The note says the original's decoder reads BMP and GIF. The spec only says that those extensions go to the general decoder and that an undecodable file silently becomes 1 x 1. Reword the note so it does not claim more than the spec. The port's behaviour (an error, which the command turns into the 1 x 1 image) may then match the original exactly.
- `file.rs:128-130`. An RLE packet that runs past the image end is an error. Tools 5.10 only says "Corrupt RLE data raises an error". Whether an overrun counts as corrupt is a port choice, and the ledger `tools.5.10.tga-loader` should name it as one.
- `contract.rs` test `an_unedited_image_decodes_lazily_and_keeps_its_bytes` does not prove laziness. Assert `img.decoded.get().is_none()` before the first `rgba()`. The field is reachable from the module's tests.
- `Image::w`, `h` and `stored` are public, and `edit()` returns `&mut RgbaBuf` with public `w`, `h` and `pixels`. A caller can make the size and the bytes disagree, or replace `stored` after decoding and leave a stale cache. The fields match the arch 6 sketch, so document the rule ("replace the image, do not resize it") or add read-only accessors.
- `alpha.rs:26`. The summed-area table holds a `u32` per texel, as much memory as the RGBA image. That doubles the arch 18 unit cost for every texture the renderer checks. A cheap win for the common binary texture: when the total count is 0, keep no table and answer `false`. Keep a separate flag for "not built", which must answer `true`.
- `pack.rs:112-130`. Every candidate size reruns the whole etagere allocation. "Create textures atlas" over 10 000 elements packs about 60 000 faces, so failed candidates repeat a lot of work. Add it to the atlas benchmark of arch 18 before it matters.
- `file.rs:172-178`. `encode_png` flips rows byte by byte through `flatten()`. `extend_from_slice` per row is simpler and faster.
- `raster.rs:84, 149`. `(x - cx) * (x - cx)` and `(to.0 - x).abs()` overflow for extreme `i32` input, which panics in debug builds. Hit texels are bounded, so this is only hardening.

## Integration notes

- W1.7 (`.cubik`): call `check_size` on `w` and `h` before `Image::from_stored`. Arch 12.3 bounds texture allocation by "`w * h` against data length". `format::decode` already allocates at most 8x the data, so only the placeholder depends on the header size.
- W1.7: `StoredPixels::raw` is an owned `Arc<[u8]>`, so retained texture bytes are copied out of the retained payload (arch 12.3), and textures sit in memory twice while retention is on. Take this into account for the 512 MiB retention cap.
- W1.7 strict recut (`atlas_recut_argb32`, native 4.5.3): for every list texture, use `format::encode(ARGB32, w, h, rgba)` and `Image::from_stored(w, h, StoredPixels { format: ARGB32, .. })`, with name "" (blocking item 2). Default textures (native 4.5.2): `format::encode(RGB24, ..)` gives exactly 768 bytes.
- Architecture: `MAX_TEXELS` (2^26) is below what the original can hold. A tall 8192 x 16384 image survives the width-only downscale, and voxel atlases and recuts can reach 16384 x 16384. A `.cubik` from Cubik with such a texture would be refused. Either record this as a deviation or raise the limit and rely on the data-length bound for records.
- App or shell: `signature` takes the ANSI code page as a parameter. This crate forbids unsafe code and cannot call `GetACP`, so the platform layer must supply the code page. On a UTF-8 system code page (65001) the digest decodes with replacement characters. Equality still works, but the value can differ from Cubik's .NET decoder, which only costs one reload (native 12 item 9).
- W2.8 (paint): arch 13.6 paints into the entry's own image, so the clip rectangle of tools 13.2 is that image. D-P6 (square brush clipped to its entry) then follows from the buffer bounds. The raster functions do not report what they changed. Dirty-rectangle uploads must take the footprint from the tool, and from the clip rectangle for fill and magic.
- W2.5 (texture ops): this crate has no bilinear resampler for the slot downscale and no crop helper (tools 5.5, 5.10). Decide whether they belong here as raster primitives or in `cuboid-ops`. The 1 x 1 image for an undecodable general file (T6) is the caller's job: `decode_file` returns an error.
