# W1.7 review (fail)

W1.7 delivers the `.cubik` container, the schema-ordered record codec, the mapping to the model with retention, the texture write policy, the extension entry, `.cub` import and the canonical dump. The file side is in good shape. Unchanged documents save the payload they were loaded from: on generated documents, and on the private sample through `apply_document` (all 4 oracle tests pass with `CUBOID_PARITY_REFS`). Edited records are encoded alone, and the documented normalisations are the only differences of a save without retention. I found no data loss on a round trip of a file Cubik writes and no wrong payload for an unchanged document. The extra entry `cuboid.json` is safe for Cubik: native 2.2 item 4 and 8.4 say Cubik ignores other entries. The writer's headers are plain (version needed 20, flags 0, method 8, no extra fields, no ZIP64, `cubik` first), which DotNetZip reads; a cross test in Cubik (native 10.3) is still open. All checks pass: `cargo clippy -p cuboid-fmt-cubik --all-targets -- -D warnings`, `cargo test -p cuboid-fmt-cubik` (92 passed, 5 ignored), the oracle tests, `cargo fmt -p cuboid-fmt-cubik -- --check`, `cargo xtask ledger --wp W1.7`, `cargo xtask layering`, and `cargo check` of the `cubik` and `cub` fuzz targets. The release perf test confirms the open of a 159 MB payload: inflate 0.25 s, decode and map 0.025 s, apply 0.004 s. The package fails on hostile input. I measured three floods with a counting allocator on release builds of the crate (a scratch probe outside the repository). Small files can make the `.cubik` loader and the `.cub` importer allocate many gigabytes, the `.cub` importer can run for a very long time, and its texture search reads any path a file names, without a cap. The ledger entry `native.8.1.hostile-input` claims bounds that do not hold.

## Blocking

1. `crates/cuboid-fmt-cubik/src/decode.rs:951` (sub-mesh count; the limit is documented at `src/lib.rs:65-66`). `max_objects` is checked per list. A file may have up to 1 048 576 meshes, and each mesh up to 1 048 576 sub-meshes, so only the payload cap bounds the total. An empty sub-mesh document is 7 bytes, because the keys of array items are ignored. It costs about 100 bytes of records (measured, `Vec` growth included). Scenario: 10 meshes with 1 000 000 empty sub-meshes each make a 70 MB payload. The crate's own level-1 writer packs it into a 537 KB archive. `load_bytes` then peaks at 1.06 GB, about 15 times the payload. At the default `max_payload` of 1 GiB, an archive of about 8 MB (less with a stronger deflate) asks for about 16 GB. An allocation failure aborts the process, and `catch_unwind` cannot catch it. The mesh data arrays (`decode.rs:914-936`) add about 5 times the payload: 10 000 000 empty vertex documents (70 MB) peak at 358 MB. The `tested` entry `native.8.1.hostile-input` says object counts are checked before allocation. For sub-meshes that is not true. Fix: count elements, meshes and sub-meshes of the whole payload against one budget kept in `Cx`. Bound the decoded items of the mesh arrays (`me.v`, `me.n`, `me.u`, `me.t`, `sm.t`) as well, or lower the default `max_payload`. Add a hostile test with many small records, and keep the entry `tested` only with that test.

2. `crates/cuboid-fmt-cubik/src/cub.rs:232-238`, `:343`, `:521-525` and `:626-642` (the `.cub` importer). The importer has no limits. Elements, texture keys and voxel cells are not counted. Each face looks its label up with linear scans of `labels` and `textures`, and `textures` grows by one entry for every new label, so the work is quadratic. `.cub` files are plain text from anywhere. Scenario, measured: a 3 MB `.cub` with 1 000 000 empty element objects peaks at 1.14 GB, about 380 times the file, so a 30 MB file needs about 11 GB. 80 000 elements that each name a new face texture (a 3.1 MB file) take 23 s to import; 20 000 take 0.6 s and 40 000 take 2.5 s. A 30 MB file of that kind runs for more than half an hour. The ledger entry `native.8.1.hostile-input` lists the `.cub` reader among the readers whose counts are checked. Fix: pass `Limits` to `cub::import`. Refuse a file larger than `max_payload` before decoding. Count elements against `max_objects`, texture entries against `max_textures`, and voxel cells against `max_array` or the voxel budget. Look labels up in a hash map from label to index. Add tests for both floods.

3. `crates/cuboid-fmt-cubik/src/cub.rs:105-106` (`DiskFiles::read`), with the candidates at `:391`, `:393` and `:403-406`. The texture search reads any path the file names. `std::fs::read` reads the whole file, with no size cap and no check that it is a regular file. `PathBuf::from(given)` is the given path itself, and `dir.join` drops `dir` when a key or an id is an absolute path. Scenario: a `.cub` with `"textures_path": {"t": "/dev/zero"}` reads until memory runs out on macOS and Linux. On Windows, `"t": "//192.0.2.1/share/t.png"` opens an SMB connection. The import stalls for the network timeout (typically about 20 s per path, so minutes with many keys), and a host that answers receives the user's NTLM hash. Fix: in `DiskFiles::read`, open the file, require `metadata().is_file()`, and read through `take` with a cap (for example the image decoder's file limit). Skip UNC and device paths, and do not join keys or ids that are absolute paths. Native 9.5 still holds for files next to the model.

## Nonblocking

- Open item, not blocking: the `.cub` model box goes to `g.mb` (`cub.rs:222-228`). Native 9.5 sets the live box only, so Cubik's own later save writes `mb` = null. The port's `.cubik` keeps the box. Cubik reads that box as the port wrote it, so the file reads the same in both programs; it only holds more than Cubik's file would. The ledger entry fits `todo` better than `unverified-spec`, since 9.5 is clear and the gap is a missing `LoadedDoc` field.
- Open item, not blocking: a transparent `.cub` element colour loads as opaque black. Cubik unpacks `c` = 0 and `c` = 0xFF000000 alike (native 4.10), so the saved file reads the same. The difference is in the session only: with "Emulate elements tint colors" off, Cubik draws such an element with alpha 0 (app 8.4). The same apply step also clamps and re-folds `.cub` UV corners outside [-1, 2] (`normal_form::uv`), which native 9.5 keeps unclamped until the save. W1.6's review asked for `.cub` import to bypass the record normal form.
- Open item, not blocking: `bp.is` is written false (`save.rs:464`). Cubik does not apply `bp.is` on load (native 4.4), so only the fresh-save golden is affected. Native 4.4 is clear, so the entry fits `todo` (blocked on the snapshot) rather than `unverified-spec`.
- Open item, not blocking: `me` and `sm` are null for primitives. Native 4.6 says `me` is null unless `tp` = 0 and types `sm` as /null, and Cubik's reader takes null for lists (native 3.6). Sample request 6 of 11.2 settles the form.
- Open item, not blocking: primitive geometry is not stored. Cubik does not store it either (native 4.6), and the writer writes `me` null. Building it is a model and renderer task (tools 6.6).
- Open item, not blocking: unknown keys are lost in re-encoded records. Cubik 2.9.480 writes none, native 8.3 makes it a SHOULD, and the entry is `todo`.
- Open item, not blocking: container byte identity and the S14 golden. Native 2.1 says container identity is not required, and S14 needs the sample.
- Open item, not blocking: the fuzz targets only type-check (confirmed). The entry says so. The deterministic hostile tests damage one valid file, so they cannot find the floods of items 1 and 2; seed the fuzz corpus with them. The comment of the `cubik` target says "whatever loads is written again", but it only encodes the decoded records. Add `apply_document` and `save_bytes` to cover the saver.
- `container.rs:108-113`: the reservation trusts the header's compressed size, which can lie too. A 138-byte archive whose headers claim 1 000 000 000 bytes reserves 1.0 GB and then loads (measured). `max_payload` bounds it and the pages stay untouched, but cap the compressed size by the archive length, or start small and let `read_to_end` grow.
- 1 000 000 empty element documents (a 7 MB payload that compresses to a few KB) peak at 1.67 GB in `load_payload`. That is within `max_objects`, but the shared budget of item 1 could be sized against memory.
- `load.rs:281`, `:428` and `:467` push one warning per record, without the cap of 64 that `decode` uses.
- Nothing enforces the 65 000-vertex limit of native 4.6.1, which is a MUST for the writer, and the ledger has no entry for it. Nothing creates such a mesh yet (OBJ import is a stub), so it is needed before L5.
- `cub.rs:37` fixes the code page of `cs` to 1252. On a Windows with another ANSI code page (for example Vietnamese, 1258), Cubik computes a different signature and reloads the texture from disk when the window regains focus (native 4.5, SHOULD). Use `EditEnv::code_page` or the platform code page.
- `dump::payload` has no size limit and writes about ten times the payload as text. The W1.11 `dump` command should bound it or stream it.
- A re-encoded root writes the loaded `v` (`save.rs:124`), not 1 as native 8.2 item 3 says. This is harmless, because Cubik never reads `v`.

## Integration notes

- Merge keeps the open document's retention (`crates/cuboid-model/src/apply.rs:477-487`). Reuse is keyed by ObjId and label, so merged records are encoded and the old ones are copied. Only Open is tested. Add a merge-then-save test when the app wires Merge.
- The app's start queue runs `default_uv(false)` on loaded elements with UV snap (`ApplyReport::created`), but the identity tests open without it. Run it in those tests once the app does, so a recomputed UV does not re-encode records.
- An unchanged `vp` depends on `CameraState` staying bit-identical when the app captures the live cameras (`save.rs:428-435`). The renderer must not rebuild the state from its own camera form unless the view moved.
- Primitive meshes load with empty geometry. Build it outside the `Mesh` value that `same_mesh` compares. Otherwise every primitive is encoded again on save: the bytes stay the same for Cubik's keys, but unknown keys are lost.
- `.cub` import needs a live model box slot in `LoadedDoc` and an apply path without the record normal form (cuboid-model).
- Above `retain_cap` (512 MB of payload), even an unchanged save is a semantic re-encode. The differences are the documented normalisations, which Cubik reads the same within the 1e-4 degree tolerance of native 4.3.2.
- W1.11 CLI: pass `Limits` through, and bound the `dump` output.
- L5: OBJ import, or the writer, must enforce the 65 000-vertex limit for Cubik-compatible saves.
- L6: do the 1 h fuzz run of native 10.4, with the record floods of items 1 and 2 in the corpus.
