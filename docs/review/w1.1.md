# W1.1 review (pass)

W1.1 passes with no blocking issues. I checked the reader, the writer and the lenient getters against native 3.1-3.6, 8.1, 8.5, 10.1, 10.2 and 10.4, and against arch 3.2, 3.3, 5, 6, 12.3 and 18. Size fields are checked against their enclosing bounds and terminators. String lengths count the NUL. Array keys are decimal indices. An f32 is widened with `f64::from` and narrowed with ties to even. An i32 rounds half to even and rejects out-of-range values, NaN included. The byte field, bool, enumeration, string, byte-array and object conversions follow native 3.6. Last-wins and document order hold, and all 21 BSON types are skipped by their length. The five native 3.5 vectors are copied byte for byte from the spec, and each is both written and read back. I checked the face-record spans by hand (uv 54..128, br 100..127). The checks are green: clippy `-D warnings`, 48 unit tests and 8 integration tests (3 ignored by design), rustfmt, `cargo xtask ledger --wp w1.1` and `cargo xtask layering`. I also ran the ignored acceptance tests. Both 10^5 differential runs against bson 3.1.0 pass (dev profile, 10 s). The S2 decode test reached 340 MiB/s (357 MB/s) in the dev profile, where workspace crates build at opt-level 1, so the 300 MB/s target is met even without full optimisation. I did not reproduce the release figure in the ledger, to save disk space. The fuzz target type-checks (`cargo check --manifest-path fuzz/Cargo.toml --bin bson`). A plain `cargo build` stops at LNK1561 because libFuzzer's entry point needs cargo-fuzz, which is not installed. The ledger states this and keeps the entry at `implemented`. The reader cannot panic on hostile input: every `len - 1` is guarded, recursion is driven by the caller and bounded by `max_depth`, and the only allocation is the base64 output. `forbid(unsafe_code)` and the arch 5 lint denials are in place. Timestamps show only owned files changed (there is no VCS to check against). The crate has no oracle-gated tests, so I did not use the private sample.

## Nonblocking

- Literal NUL bytes in the source: `crates/cuboid-bson/src/writer.rs:27` (a doc comment showing `b"uv<NUL>"`) and `crates/cuboid-bson/src/convert.rs:214, 218, 222, 226` (`b"v<NUL>"`). Git treats a file with a NUL in its first 8000 bytes as binary, so diffs of writer.rs will show "Binary files differ". The bytes in convert.rs are invisible in editors. Write `\0` instead, as the rest of the crate does.
- Some `tested` ledger entries include choices that the spec does not make. `native.3.6.byte-array` (w1.1.toml:244) fixes a base64 dialect: only space, tab, CR and LF are skipped, padding is required, and non-zero trailing bits are accepted ("AR==" decodes like "AQ=="). The comment at convert.rs:133 models this on .NET's `Convert.FromBase64String`, which is a guess about Cubik. `native.3.6.object-list` (w1.1.toml:266) says arrays are read "whatever their keys", which native 3.1 and 3.6 do not say. `native.3.6.f32` says int64 rounds once. Similar choices (boolean-byte, enum-edge-forms, invalid-utf8, old-binary-length) already have their own `unverified-spec` entries. Do the same for these (21.1 rule 5).
- The note of `native.8.1.trailing-bytes` (w1.1.toml:315) says the spec is silent, then states as fact that Cubik's reader stops at the end of the root document. Cite native 3.1 ("relies on the size fields to find the end of each document") as the basis, or call it an inference.
- `arch.12.3.bson-differential` (w1.1.toml:366) and `arch.18.bson-decode-throughput` (w1.1.toml:381) are `tested`, but the tests that carry the acceptance numbers (the two `_100k` runs and the timing test) are `#[ignore]`. CI never runs them, and parity/README.md defines `tested` as "pass in CI". The notes say so. Add the run to a scheduled job so the claim stays checked.
- `crates/cuboid-bson/src/dump.rs:22`: `dump` builds one String and repeats the full path on every line. Its size is key length times element count. A 1 MB hostile payload with a 500 KB key over about 160 000 nulls asks for about 80 GB. A valid S2 payload already dumps to about 760 MB. The fuzz target's inputs are too small to hit this. A `dump_to(&mut impl fmt::Write)` (or `io::Write`) variant would let the CLI stream its output.
- `crates/cuboid-bson/src/writer.rs:16-25`: a key without its NUL is caught only by `debug_assert`. In a release build it silently writes a broken document. Schema keys are constants, so a const constructor that fails at compile time would make this check free for the W1.7 tables.
- `crates/cuboid-bson/src/writer.rs:119-125`: `end` trusts the Mark. A mark from another writer, or closing an outer document before an inner one, gives wrong sizes with no error. A mark past the end of the buffer also causes an overflow panic in debug builds. Arch 6 sketches an open-document stack, and a debug-only stack check would catch such bugs in W1.7 tests at no release cost.
- `crates/cuboid-bson/src/reader.rs:187`: `last` walks the whole document on every call, so a decoder that calls it once per key costs O(keys x members). Its doc comment should tell decoders to make one pass over `iter()` and overwrite on repeated keys.
- `crates/cuboid-bson/src/error.rs:26-35`: `BadUtf8`, `WrongType`, `OutOfRange`, `BadBase64` and `UnknownName` carry no offset, while the other variants do. Callers can add `elem.value.start` themselves, but a uniform `at` field would make messages consistent.
- `crates/cuboid-bson/src/convert.rs:93-112`: `bytes_opt` calls `value()` first. A document or a bad boolean in a byte-array slot therefore reports `TooDeep` or `BadBool` instead of `WrongType`. This is cosmetic.
- Several public items have no doc comment: `Limits::DEFAULT`, `DocWriter::new`, `with_capacity`, `i32`, `i64`, `bool`, `null`, `str`, `ElemType::from_byte` and the `Span` fields.

## Integration notes

- The code differs from the arch 6 sketch. `enum_i32` takes `(name, value)` pairs instead of `&[&str]`, which is better because enumerations can have gaps (the test uses 63). `DocWriter` has `begin_root`, `begin_doc` and `begin_array` instead of `begin(Option<key>)`. Keys are `impl Key`: NUL-terminated static bytes or a `usize` index. The crate also adds `f64`, `i64`, `finish`, `as_bytes`, `with_capacity`, `RawElem::{u8, array, value, value_bytes}` and `Value`. Update arch 6 or record the change in 17.4, and have W1.7 code against the crate, not the sketch.
- `sha2` is now a runtime dependency of cuboid-bson, used by `dump`, so it ships in the app. Arch 4.1 does not list it, and 17.4 M0-4 names only the test kit. Update one of them.
- Arch 12.3 lists, under the BSON bullet, the quaternion `eulerAngles` override and the texture `w * h` and voxel resolution limits. Under arch 3.2 the crate cannot know records, and the ledger header hands these rules to fmt-cubik. W1.7's ledger must carry them: the native 3.4 override applied in document order, null treated as absent with a warning for value-type keys (native 3.6), a null Unity vector, missing-key defaults, and the texture and voxel limits of native 8.1 item 4. Consider moving these rules in 12.3 under fmt-cubik.
- For W1.7: parse the whole decompressed payload once. Every `Span` is relative to the buffer given to `RawDoc::parse`, so spans then index the retained `Arc<[u8]>` directly. Parsing a sub-slice later gives offsets relative to that slice and resets the depth. Keep unknown elements as their `whole` span. A retained array item whose index changed can be rewritten with `begin_doc(i)`, `raw(&doc.as_bytes()[4..len - 1])` and `end`, with no new API. Check `elem.ty == ElemType::Null` before calling the value-type getters. Pass tighter `Limits` where the format allows.
- For W1.11: cuboid-cli depends on core, io and fmt-* (arch 3.3), not on cuboid-bson. The native 10.2 dump also needs the extra RawTexture `r` lines, which only fmt-cubik can compute. fmt-cubik should therefore expose the payload dump. A per-element hook in cuboid-bson's `dump` would let it add those lines without a second copy of the traversal, and that hook is cheap to add here now.
- The 1 h fuzz run is still owed. It needs `cargo install cargo-fuzz` (0.13.2, arch 4.3) and the nightly toolchain, which is installed. The ledger has no status for "fuzzed clean", so the integration role should decide how the nightly result is recorded. `native.10.4.fuzz` stays `implemented` until then. A seed corpus made from the native 3.5 vectors would help the fuzzer.
- The release decode figure in the ledger (851-864 MiB/s) was not re-measured here. W7.1 should measure it on R1.
