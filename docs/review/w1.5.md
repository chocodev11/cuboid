# W1.5 review (fail)

W1.5 fails on four blocking items: quarter turns move and swap raw UV corners instead of folded ones, the selection operations never maintain the highlight set, `stable_partition` cannot see which items are selected, and the invariant checker rejects documents that loads and imports produce legally. Most of the package is right. Position propagation moves position and origin of the other selected objects, and the model origin writes `g.o`. The size setter rescales about the pivot with the unclamped ratio and clamps afterwards. The rotation setter wraps with the dividend's sign, rounds half to even to 5 or 22.5 degrees, counts a stored 360 as rotated, rejects after propagation, rotates about the pivot with R_new * R_old^-1 and turns UV snap off. The bake follows the six steps of tools 3.5. The X and Y quarter turns match the tools 4.9 table (maps, fix-ups, sizes, face cycles, UV spins). I checked these by hand, together with all eight rows of the tools 4.7 table against the test values, the folding getters and rotated corners of tools 4.5, the model box clamp order of tools 2.4, and the default face label rule. The coordinator decisions hold: a `Texture { name, source, image }` record over a raster `Image`, `set_active_box` for the model box, process-wide ObjIds that are never reused, and plain-data setter options. The Z quarter turn: the spec does say it. The Z row gives (x, y, z) -> (y, -x, z), the stated composition X(+90), Y(+90), X(-90) evaluates to exactly that, and so does the MC-space line. With the engine convention of tools 1.3, +90 about Z is (-y, x, z), as the `euler_to_quat` assertion in the test shows. Only the sentence "R the engine rotation for +90 degrees about the axis" disagrees. The ledger handles this correctly: the code follows the table, and `tools.3.5.restriction-bake-z` is `unverified-spec` with the reason and a test that pins the -90 behaviour. Clippy with `-D warnings`, 86 tests (W1.6 files included, they compile), rustfmt, `cargo xtask ledger --wp w1.5` and `cargo xtask layering` all pass. Only owned files and `contract.rs` changed (by modification time), and the crate forbids unsafe code.

## Blocking

1. `crates/cuboid-model/src/setters.rs:356-365` (ledger `tools.4.9.quarter-turns`, `w1.5.toml:380`, and both bake entries, which run the same code). The face cycle clones each face with its raw corners and swaps the raw corners of the faces arriving at down and north (`set_unclamped(br, tl)`). Tools 4.4 says internal face moves are face copies. Tools 4.5 says copies use the folded values ("All consumers (mesh UVs, files, copy) use the folded values"), and so do arch 8.3 and tools 16.1. Folding is not symmetric under a swap when a rectangle straddles 0 or 1, so a raw swap gives a different rectangle than a swap of the folded corners.
   - Scenario: the north face has raw tl (-0.25, 0) and br (0.5, 1) after a drag across the left edge in the UV view. It reads (0, 0)..(0.5, 1). An X quarter turn moves it to down. Swapping the folded corners gives (0.5, 1)..(0, 0), the same strip turned 180 degrees. The port stores raw (0.5, 1)..(-0.25, 0), which reads (0.5, 1)..(0.75, 0): a different, narrower strip. A rotation drag in restricted mode calls the same code through the bake. Moved faces that are not swapped also keep raw corners outside [0, 1], where the original stores folded ones; this shows once the UV view edits them. All tests use in-range rectangles, where raw and folded agree.
   - Fix: in `quarter_step`, give each moved face the folded corners before the swap, for example `face.uv = UvRect::new(face.uv.rot(), face.uv.tl(), face.uv.br())`. The swap that follows is then a swap of folded values. A small face-copy helper with a keep-name flag in `objects.rs` would give W2.x the same rule for the other face copies (tools 10.8, 10.17). Add a test with a straddling rectangle on north and on up.

2. `crates/cuboid-model/src/selection.rs:30-59` (ledger `tools.8.1.selection-operations`, `w1.5.toml:115`, test `clear_keeps_the_highlight_set`). `add`, `toggle`, `remove` and `clear` never touch `highlighted`, and `clear` is documented and tested as keeping it. Tools 8.1 defines clear as "deselect all, primary none". Select all and select by name empty the list without un-highlighting, and the spec marks that as a QUIRK, so a normal deselect does un-highlight. Arch 8.5 says `Selection` implements tools 8.1 and keeps the highlight set apart only because of that quirk. The ledger records the quirk behaviour of `clear` as parity.
   - Scenario: click element a, then click empty space (select exclusive with no object, which clears). Either a was never outlined, because `add` does not highlight, or, if the caller highlights on add, a stays outlined after the clear, as if select all had run. Every caller would have to rebuild the highlight rules of tools 8.1 itself. The field doc ("Objects drawn with the selection outline") is not what the operations maintain.
   - Fix: `add` inserts into `highlighted`; `remove` (and the remove branch of `toggle`) removes the object from it; `clear` removes every listed object from it and keeps the others (leftovers of the quirk). Select all and select by name keep the quirk by emptying `list` directly, keeping `primary` and `highlighted`; a named method would document that. Update the test and the ledger summary.

3. `crates/cuboid-model/src/list.rs:194` (ledger `tools.10.7.stable-partition`, `w1.5.toml:73`). The predicate of `stable_partition` gets only `&T`. Tools 10.7 partitions by selection ("selected elements first/last"), and neither `Element` nor `Mesh` holds its `ObjId` or a selected flag. `restore` renumbers display ids, and remove plus push issues new ObjIds, so this is the only reorder that keeps identity. W2.2 can only write Move to top/bottom (and the mesh versions) by comparing addresses inside the `Arc`s, which the contract does not promise. So W2.2 would have to change `list.rs`.
   - Scenario: W2.2 implements "Move to top" for the selection {b, d} of [a, b, c, d]. The closure receives `&Element` for each item and has nothing to test membership with.
   - Fix: `pub fn stable_partition(&mut self, mut front: impl FnMut(ObjId, &T) -> bool)`, called with `(self.ids[pos], &self.items[pos])`. Update the two tests and note the change from the arch 6 sketch in the ledger header, like the texture record.

4. `crates/cuboid-model/src/invariants.rs:75-79` and `:108-110` (ledger `arch.8.7.object-invariants`, `w1.5.toml:425`, and `arch.8.7.voxel-invariants`, `:449`). The checker applies setter-only rules to every object. It rejects documents that the spec says are valid results of a load or an import. Cube elements keep stored sizes below 0.001 (native 6.3, "sizes"). Mesh scales are applied as stored (native 4.6, 6.3). The `.cub` and Minecraft JSON importers store UV corners without the [-1, 2] clamp (native 4.4.3, 9.5). Import mode can force a palette duplicate (tools 7.4). Arch 8.7 limits the size rule to "sizes from the size setter", and arch 8.3 says bypass paths "are excluded from the size invariant". The checker cannot exclude anything, and the ledger records only the dialog and palette cases. Arch 8.7 also runs the checker in the fuzz harness and after every command in debug builds. So W1.7's fuzz targets, W1.6's property tests over loaded records, and the core's debug check after File > Open will report false failures, and the fix has to be made in this file.
   - Scenario: open a `.cubik` whose element record has `s` = (0.0005, 1, 1), or import a `.cub` with a corner at 2.5. The load is correct and Cubik shows the same document, but `check_invariants` returns `SizeBelowMinimum` or `UvCornerRange`.
   - Fix: separate the rules that hold for every document from those that hold only for setter output. One option: keep `check_invariants` for documents built through the setters, and add an entry point (or a scope argument) for loaded and imported documents that skips the size minimum, the raw-corner range and palette distinctness. Another option: a per-document exemption set that the load, import and dialog paths fill. Either way, record the load and import cases in the ledger.

## Nonblocking

- `list.rs:162-168` with `list.rs:240-244`. `push` inserts the new id into the lookup map and then `touch_structure` throws the map away, so the insert is dead code. After every push, the next lookup rebuilds the whole map. A loop that pushes an object and then opens a guard on it (paste of tools 11.3, merge, the conversions of tools 14) is O(n^2). For 10 000 elements that is about 5 * 10^7 map inserts, far beyond the 150 ms of arch 18. Keep the map on push and reset only the stamps there. Fix this before W1.6 builds paste on it.
- `contract.rs:619-624` and ledger `tools.2.3.blueprint-default` (`w1.5.toml:130`). `Document::new` is documented as "the document after File > New ... the blueprint at its scene default", and the ledger says "a new document uses it". Tools 2.3 says a new model does not reset the blueprint, and app 1.3 keeps the camera poses, which `view: Arc::default()` resets. The function is right for start-up. Say that in the doc and the ledger, and leave File > New to W2.1 (keep the old blueprint and cameras).
- `w1.5.toml:380` (`tools.4.9.quarter-turns`). The entry is `tested` for Z too but does not mention the conflict recorded in `tools.3.5.restriction-bake-z`. Add the note there, or split the Z turn into its own `unverified-spec` entry, since W2.3's model rotation (tools 10.11) uses the turn without a bake.
- `w1.5.toml:394` (`tools.4.9.faces-only-variant`, `todo`). The face tables live only in `quarter_step`. Splitting it into a geometry half and a faces half gives the faces-only variant for free now. Otherwise W2.4 either copies the tables or has to edit `setters.rs`, which the note itself expects.
- `setters.rs:197-206`, `:273-278`, `:261-265` and `:313-315`. `set_origin_move` writes the origin (journal entry, new document revision) even when it is unchanged. Rotation propagation writes the pivot unconditionally, and removing UV snap journals even when the flag is already off. The summary of `arch.8.6.setters-journal` (`w1.5.toml:98`) says a setter that changes nothing leaves the journal and the revision alone, which is not true for `set_origin_move`. A spurious revision also drops worker results (arch 8.1). Guard the writes with `engine_eq` or `contains`, or narrow the summary.
- `uv.rs:247-255`. `the_default_mapping_reads_the_stored_position_of_a_rotated_element` maps two unrotated positions. Item 6 asks for a rotated element. Add a guard-level test: rotate an element about a pivot away from its corner, call `default_uv(true)`, and compare with `default_uv_rects` at the rotated `p`.
- `w1.5.toml:247` (`tools.4.7.propagated-objects-remap`). The behaviour has no test. Add one where a snapped non-primary element remaps after a propagated move and a propagated resize.
- `setters.rs:292-295`. `quarter_turn` normalises with `rem_euclid` and returns before the reset when the turn count is 0. Tools 4.9 uses `mod` with the sign rule of tools 3.4, so an angle below -360 gives a negative count, and the spec does not say whether a zero turn still resets the rotation and turns snap off. The bake never passes such angles, but W2.3 might. Mention both choices in the quarter-turn entry.
- `setters.rs:536-549`. The propagation step of the bake skips selected objects that are not elements. Tools 3.5 step 1 says "every other selected object", and the blueprint is restrictable. This is probably right, since the bake is an element operation, but record it.
- `w1.5.toml:466` (`arch.8.7.structural-invariants`). `unverified-spec` is meant for open spec questions. These two rules hold by construction, so `implemented` with the same note describes them better.

## Integration notes

- Coordinator and W2.3. File the Z quarter-turn question against tools 4.9 (open questions in tools 18), as arch 21.1 rule 5 asks. Until it is settled, `quarter_turn(Axis::Z, 90)` turns by the engine's -90 degrees, so "Rotate model +90 on Z" (tools 10.11) will too.
- W1.6 and W2.1. `EditEnv.restrict_rotations` is a copy of `props.general.restrict_rotations`. Load and restore must quantise with the loaded `g.rer` (native 6.3), so build the environment from the new properties for the object step. The bake that runs when the restriction is switched on must see `restrict_rotations = true`, or step 5 re-rounds 22.5 to 20 on the 5-degree grid.
- W1.6. `set_rotation` returns `Unchanged` for a request equal to the stored rotation, and native 6.3 does not normalise such a rotation either. Re-quantising a restored or loaded record therefore has to start from `e = 0` (the "new object" case) or use `wrap360` and `snap_angle` directly.
- W2.x and W3.x. List operations (`push`, `remove_set`, `stable_partition`, `restore`, `clear`) and selection operations do not write the journal. Callers mark `DocFlags::LISTS`, `SELECTION` and `HIGHLIGHT`, or scene sync compares `structure_rev`. Blueprint changes have neither an object entry nor a `DocFlags` bit, so scene sync must compare the blueprint itself each frame, unless a `BLUEPRINT` bit is added.
- W2.9 and W2.3. There is no guard for the model origin. A drag of the model origin calls `set_model_origin`. If it is the primary with other objects selected, propagate with `set_origin_move(o + delta, false)` on each of them, which moves `p` and `o` together. Tools 3.2 `moveTo(target)` is `set_origin_move(target + (o - p), ...)`.
- W2.2. Tools 10.1 copies the blueprint's orientation into a new element's transform without its stored rotation (QUIRK). The model keeps only `e`, so the quirk cannot be represented. Record a deviation, or ask for a field before W3 draws elements.
- W2.2 and W2.4. Face copies in tools 10.8 and 10.17 must use folded corners as well (blocking 1). `UvRect` has no helpers for the 0..1, 16-pixel and atlas rectangle setters of tools 4.5; they are easy to build on `set`.
- W1.7. `MeshGeometry.uvs` is a `Vec`, so a null `u` and an empty `u` (native 4.6.1) load the same; list that as a normalisation. Face names are an enum, so a nonstandard `n` string in a file cannot round-trip either.
- W1.6 and W1.7. `Mesh` and `Texture` do not implement `PartialEq` (the image has none), so the reference-twin comparison needs the normal form for meshes and textures. `Element` does implement it.
